## 1. Executive Summary & Problem Context

The enterprise operated on a legacy on-premise Oracle Exadata data warehouse that supported global commercial transactions, supply chain inventory, and financial reporting. 

Over a 5-year period of rapid transaction growth, the legacy system suffered from critical operational bottlenecks:
- **Nightly Batch Exhaustion:** Heavy ETL transformations ran 6 to 8 hours overnight, consistently breaching business-critical SLAs before market opening.
- **Resource Contention:** Concurrent analytical queries from BI teams choked active ingestion batches, leading to lock contention and high operational maintenance overhead.
- **Licensing & Scaling Wall:** Scaling vertical capacity on-premise required prohibitive hardware procurement cycles and exponential licensing fees.

**The Objective:** Lead the end-to-end architectural design, data modeling, and zero-data-loss cutover to **Google BigQuery**, establishing a decoupled compute-and-storage modern data platform.

## 3. Engineering Decisions & Architecture Trade-Offs

### A. Partitioning & Clustering Strategy

BigQuery costs and execution speed depend strictly on bytes scanned. For high-volume transaction tables:
- **Partitioning:** Ingestion timestamp partitioning (`_PARTITIONDATE`) was applied on append-only streams, preventing full-table scans.
- **Clustering:** Multi-column clustering on `(merchant_id, store_id, transaction_status)` was implemented. This matched the high-cardinality filters of 90% of downstream commercial queries.

```sql
-- Production DDL pattern for high-scale transaction log
CREATE OR REPLACE TABLE \`production_dw.fct_commercial_transactions\`
(
  transaction_id STRING NOT NULL,
  merchant_id STRING NOT NULL,
  store_id STRING NOT NULL,
  transaction_timestamp TIMESTAMP NOT NULL,
  gross_amount NUMERIC(12, 2),
  fee_amount NUMERIC(12, 2),
  transaction_status STRING
)
PARTITION BY DATE(transaction_timestamp)
CLUSTER BY merchant_id, store_id, transaction_status
OPTIONS (
  require_partition_filter = true,
  description = "Partitioned commercial transactions log with mandatory filter"
);
```

### B. Slot Reservation vs. On-Demand Pricing

To eliminate surprise queries running up runaway cloud bills:
1. Production ELT DAGs were pinned to a dedicated **Flat-Rate / Capacity-based Slot Reservation** (500 slots) with burst capacity.
2. Ad-hoc BI exploration remained isolated in a distinct project with per-user byte scan limits enforced via BigQuery custom query limits.

### C. Zero-Data-Loss Dual-Run Validation

Prior to the cutover window:
- Implemented an automated reconciliation pipeline using **PySpark** running checksum and row-count drift calculations between Oracle extracts and BigQuery tables across 90 rolling days.
- Zero discrepancy was certified across **2.4 TB/day** before decomissioning legacy database links.
